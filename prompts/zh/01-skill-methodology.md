帮我创建一个 Skill：`tdp-inspection-methodology`。

**用途**：ThreatBook TDP（NDR 产品）巡检的**研判方法论**。当需要研判 TDP 告警性质、
判断某台主机是扫描器还是真实横移、判断某个行为是威胁还是客户自有行为、给巡检结论定级、
或撰写 TDP 巡检报告时载入。

**边界**：本 skill 只管**怎么判**。采集、降噪、统计、交叉这些确定性计算由配套 workflow 完成，
skill 不含采集步骤，不替代 workflow。

这个分工的理由：精确计数、去重聚合、两表 join 是 LLM 最不可靠的地方，交给 workflow；
定性判断、家族归因、叙事是 LLM 擅长的，交给 skill。

## 方法论正文

### 0. 开工前必须先确认的一件事

**PoV / 测试期间，我方有没有做过模拟攻击或样本投放？不许假设，不许默认。**

| 模式 | 含义 | 定性框架 |
|---|---|---|
| A | 我方做过模拟攻击/投放样本 | 我方流量归「检出能力验证」，客户真实流量归「实网发现」，**两者必须分开写** |
| B | 纯真实流量旁路监听（更常见） | **没有「我方测试」这一档**，所有告警都是客户真实环境的真实流量 |

这个前提定错，整份报告的定性会系统性偏掉。模式 B 下最容易犯的错：
把客户自己的安全工具（漏扫、BAS、红队）、IT 运维行为（运维隧道、批量推送）、
员工行为（远控软件）当成攻击报出去。这一档**只有客户能认领**——给倾向和依据，绝不代客户断定。

### 1. 六层框架（巡检是漏斗，前一层不成立后一层就没意义）

| 层 | 回答什么 | 关键产出 |
|---|---|---|
| 0 可信度 | 这份数据能不能信？ | 可信度评级 + 降权声明 |
| 1 资产实况 | 网里实际有什么？ | 暴露面清单（三切面） |
| 2 威胁实况 | 网里在发生什么？ | 定性后的事件清单 |
| 3 交叉关联 | 哪些资产两头都占？ | **处置优先级队列** |
| 4 检测效能 | 设备干得怎么样？ | 信噪比 + 调优清单 |
| 5 运营成熟度 | 客户处置得怎么样？ | 管理面建议 |

**第 0 层是门槛**：引擎过期、云情报不可达、镜像口异常、采集有缺口时，
后面所有「未发现威胁」的结论**都可能是漏报而非真干净**，必须在报告第一页声明降权。

**第 3 层是核心**：第 1、2 层单独看设备自己的报告也能给，
但没有任何现成报告把两边 join 起来，而真正的高危恰恰只在交叉处出现。

### 2. 流量定性三分法（唯一强制人审点）

每个进入研判的事件，结论必须落到四档之一，不许跳过、不许默认：

| 定性 | 特征 | 处置取向 |
|---|---|---|
| `real_threat` | 命中情报、`is_connected=1`、`result=success`、真实数据外流 | 立即处置 |
| `customer_own_behavior` | 客户自有安全工具/IT 运维/员工行为——真实但非攻击 | 治理决策，**只有客户能认领** |
| `tdp_artifact` | 统计假象、机制产物 | 排除，但要说明为何排除 |
| `pending_review` | 证据不足以定论 | 列证据交人裁决 |

**铁律**：把真实威胁当演练、或把客户自己的扫描器当失陷，是巡检最危险的两个错误。
**存疑就标存疑**，绝不替客户对生产环境流量拍板。

### 3. 失陷判定优先级

1. `threat.is_connected = 1`（C&C 建连成功）—— **最硬信号，优先级高于「攻击成功」**
2. `threat.characters` 含 `is_compromised`
3. `threat.result = success`

失陷主机必查**次生行为**：有没有再对内横移/对外攻击。失陷 + 扩散 = 定级上调。

`result = unknown` **不等于**没成功。旁路检测无法确认结果时，
要结合目标补丁状态和后续行为综合判断，不能简单当「未成功」放过。

### 4. 扫描器 vs 真实横移（三条同时成立才下结论，且全部用相对量）

1. 单源打击的**目标数量级**远高于全网中位数
2. **威胁种类爆炸**——一台主机涌现大量互不相关的漏洞家族
3. 结果**以失败/未知为主**

三者齐 -> 高度疑似扫描器或攻击模拟器。但在模式 B 下，
**它是客户的安全工具还是被控主机在横扫，只有客户能认领**——必须交裁决。

**绝不用绝对阈值**（「打了 100 个目标」「超过 5000 条」），换个客户环境立刻失效。一律用相对基线。

### 5. 隧道类单独拎出来

`threat.type = tunneling` 即使量小也要单独报：它绕过边界管控、加密不可审计、
只要进程在跑外部就能直连内网。定性是**治理问题**不是恶意软件问题——
要么正式纳管，要么移除，「不知道它在那里」不行。

### 6. 定级自洽性检查

设备给的总体态势等级与逐项发现必须自洽。若出现「态势等级偏低但存在确认失陷/成功的后门通信」：
在报告里**明确指出矛盾**并给建议（如复核态势阈值配置）。
**不盲从**设备定级，**也不擅自改写**——呈现矛盾，给建议，让客户定。

### 7. 各层研判要点

**第 1 层资产**：每类资产过三切面（对外暴露/新发现/带风险）。
「新发现」有两个口径（设备标记 vs 与上次巡检 diff），**含义不同不得混用**，分开印。
EOL 中间件是结构性风险，优先级高于普通漏洞。未识别服务是盲区，不是「没风险」。
弱口令要看登录结果：检出弱口令且有成功登录 = **已被利用**，不只是隐患。
资产数字必须标注时间窗——NDR 看到的资产是「窗口内说过话的资产」。

**第 4 层效能**：信噪比要用**设备返回的全量基数**算，不能用被分页截断的明细数。
疑似误报要给**可执行的调优动作**（建忽略规则/告警重分类/补 X-Forwarded-For/登记反代资产），
不能只说「这是误报」。某攻击阶段数据完全空白，通常是部署位置或采集配置问题，不是「真没有」。

**第 5 层运营**：未处置比例高 = 缺流程或缺人，不是设备问题。
资产名大量是默认值 = 未建资产台账。这层建议写给管理层，不要写成技术动作。

### 8. 红线

1. **只读**。不做任何阻断、改处置状态、改配置、加规则的动作。巡检工具不改变被巡检对象。
2. **IOC 富化只用 ThreatBook 情报**。禁止 VirusTotal / AbuseIPDB / 任何第三方源参与 IOC 定性——
   这些工具在环境中可能是启用状态，看到也不要用。
3. **只写实际查到的**。没查到的标「未富化·待人工」，绝不编造来源、链接或结论。
   也不要写「公开源查不到」这类未经授权的来源对比。
4. **不落明文口令**。只写用户名、口令长度与强度特征、命中规则。
5. **不夸大、不拍板**。存疑列证据交客户。
6. **术语对齐产品英文 UI，不自创译法**：Inbound Attack / Lateral Movement / Compromised /
   alert / incident / TCP reset / Attack Surface / Weak Passwords / Resolution Status。
