# TDP 24 小时巡检

对一台已接入的 TDP 做**只读**巡检，产出**英文客户面报告**。

设备只会告诉你「命中了什么规则」。**巡检的增量全在研判和口径**——同样一批告警，
判成「客户内网有台机器在横扫」还是「客户自己的漏扫工具在跑」，处置动作天差地别。

TDP 自带的导出报告会罗列告警和资产，但 `Security Recommendations` 一章是空的
（原文 `(Input by inspectors, ...)`），且不做研判、不做降噪、不做维度间关联。本 skill 补这三块。

---

## 0. 开工前必须确认（不许假设，不许默认）

### 0.1 设备名

问用户巡检哪台设备。**不要猜**。用 `/tools` 或设备列表确认设备已连接。

### 0.2 `pov_mode` —— 最关键的一个前提

> **这台设备所在环境，我方有没有做过模拟攻击 / 样本投放？**

| 模式 | 含义 | 定性框架 |
|---|---|---|
| **A** | 我方做过模拟攻击／投放样本（自建测试环境、PoV 演示环境常见） | 我方流量归 **detection capability validation**，其余归 **live-network findings**，**两者必须在报告里分开成节** |
| **B** | 纯真实流量旁路监听 | **没有「我方测试」这一档**。所有告警都是该环境的真实流量 |

**默认怀疑方向是 B。** 本 skill 的主用途是真实环境巡检（给客户做 demo 只是顺带），
所以除非用户明确说做过模拟攻击，否则按 B 处理——**把真实威胁误当成我方测试流量放过，
比多问一句严重得多**。

**这个判错，整份报告的定性会系统性偏掉。**

模式 A 最容易犯的错：把我方打的攻击当成"客户环境里的真实威胁"报出去——
拿给客户看会闹笑话，而且掩盖了真实发现。
模式 B 最容易犯的错：把客户自己的安全工具（漏扫、BAS、红队）、运维行为（隧道、批量推送）、
员工软件（远控）当成攻击报出去。这一档**只有客户能认领**。

## 1. 时间窗：先对时，再取数

**第一件事是调 `tdp_system_status` 看时区状态。** 时区不对，24 小时窗口整个取歪，
后面所有数字都是错的。

- `time_to` = 当前 Unix 秒（**动态计算，绝不硬编码**）
- `time_from` = `time_to - 86400`
- 报告里必须印出两个时间戳对应的可读时间和时区

### ⚠️ 不是所有维度都能按 24 小时切（本 skill 最容易出错的地方）

TDP 的接口分两类，**时间语义完全不同**：

| 类别 | 接口特征 | 语义 | 报告里怎么写 |
|---|---|---|---|
| **窗口型** | 接受 `time_from` / `time_to` | 真的是近 24 小时发生的 | "In the last 24 hours…" |
| **快照型** | **不接受时间窗参数** | 设备**当前**的全量状态 | "As of \<timestamp\>…" |

**已知的快照型**（不接受时间窗，返回当前全量）：攻击面总览 / 对外暴露资产 / 新发现资产、
攻击链阶段统计、恶意文件检测、登录入口风险、Web 应用、服务分类、数据泄露拓扑。

**所以报告里绝不能写「近 24 小时的攻击面是 X 个」**——那是当前攻击面，不是 24 小时新增。
每一节的标题和数字都要带对应的时间语义。混用会让客户误判"一天之内冒出这么多暴露资产"。

> **已定（不必再验证）**：攻击面一律按**当前状态**写，不去凑 24 小时口径。
> 即使 3.3.10 连接器真的接受时间窗，也按当前状态呈现——攻击面本来就是存量概念，
> "24 小时内的攻击面"对客户没有意义，反而容易被误读成"一天新增这么多暴露资产"。

## 2. 固定阶段顺序（不许跳，不许换序）

```
Phase 0  可信度      设备健康 -> 决定后面所有结论要不要降权
Phase 1  态势总览    dashboard 各切面
Phase 2  威胁实况    24h 告警与事件（窗口型）
Phase 3  统计基线    terms 聚合 -> 相对基线与信噪比
Phase 4  攻击面      资产六类（快照型）
Phase 5  风险隐患    脆弱性 / 弱口令 / 敏感信息
Phase 6  研判定性    三分法 + 交叉关联
Phase 7  成文        英文客户报告
```

**为什么 Phase 0 必须最先**：引擎过期、云情报不可达、镜像口异常、采集有缺口时，
后面所有「未发现威胁」的结论**都可能是漏报而非真干净**。先知道数据能不能信，再去解读数据。

**为什么 Phase 3 在 Phase 4 之前**：相对基线（中位数、占比）要在做资产判断前算出来，
否则 Phase 6 的扫描器判定没有分母。

具体每个阶段调哪个工具、传什么参数、有哪些坑，读 `references/tool-playbook.md`。
**那份是执行手册，开工前先读，不要凭工具名猜参数。**

## 3. 逐阶段自检（Skill 路线的成败在这里）

工作流可以用 Python 保证计数准确，本 skill 靠 LLM 编排，所以**每个阶段必须显式自检**。
下面每条都是硬要求，做不到就在报告里声明，**不许静默略过**。

### 3.1 分页自检（最容易造成事实性错误的一条）

列表类接口**默认每页只返回 20 条，且不会自动翻页**。实测 `service_list` 默认返回 20 条，
而 `page.total_num` 是 445 —— 只取到 4.5%。**把 20 当成资产总数写进报告，整份攻击面分析作废。**

每个列表调用后必须：

1. 读响应里的 `page.total_num` 与 `page.total_pages`
2. 循环翻页直到取全（或达到你设定的上限）
3. **对账**：取回条数 != `total_num` 时，该项记 `partial`，把「实际取到 N / 总数 M」写进 `coverage_gaps`
4. **报告里任何资产数字都必须是 `total_num`**，不是本次取回的条数

### 3.2 聚合 size 自检

`tdp_log_search` 的 `size` **默认只有 10**。做聚合统计必须显式调大（建议 200–1000）。
该工具**不支持** `page_size`，别传。

用默认 10 做 TOP 统计，等于只看了前 10 个值就下"噪声来源"的结论。

### 3.3 聚合降级自检

`action=terms` 实测**可能整个不可用**（服务端能力缺失，不是参数问题）。不可用时按序降级：

| 优先级 | 数据源 | 代价 |
|---|---|---|
| 主 | `tdp_log_search action=terms` | 有 `global_total` / `global_percent` / `distinct`，统计最准 |
| 备 1 | `tdp_threat_intelligent_aggregation` | 设备侧已做过一轮聚合 |
| 备 2 | `tdp_threat_alert_host` 的主机级聚合 | 只能算主机维度基线 |

**降级后必须在报告的口径说明里写清**：信噪比的分母不再是全量精确值，
只能给"基于主机级聚合的估算"，**不得当成精确占比呈现**。

### 3.4 容错自检

任一工具失败、超时、或该模块客户未订阅 → 记入 `coverage_gaps` 并**继续**，
**绝不中断整个巡检**。所有 `coverage_gaps` 直接进 Phase 0 的可信度声明，
报告第一页明写"本次未覆盖 X / Y / Z"。

### 3.5 攻击面口径冲突处置（Phase 1 与 Phase 4 会打架）

Phase 1 的 dashboard 攻击资产切面和 Phase 4 的资产六类**是两套口径**，数字大概率对不上
（前者是设备侧汇总，后者是明细列表的 `total_num`）。报告里一处写一个数，客户一眼看出矛盾。

**规定**：

- 报告正文的攻击面数字**一律以 Phase 4 的 `total_num` 为准**——它可追溯到具体列表接口
- Phase 1 的 dashboard 数字**只用于交叉校验**，不直接进正文
- 两者差异超过 10% 时，在附录「数据口径说明」里记录两个数字和各自来源，
  **不要自己挑一个好看的写**，也不要试图解释成因（除非确有证据）

### 3.6 数字可追溯自检

**报告里每一个数字，都要能指回是哪个工具、哪次调用、什么时间窗取的。**
指不回去的数字不许写进报告。这条是防 LLM 顺手编数字的最后一道闸。

## 4. 研判

### 4.0 威胁怎么分类（三个正交维度，分层用）

**别把它们混成一级目录。** TDP 原生就给了这三层，不需要自己发明分类法：

| 维度 | 字段来源 | 用在哪 |
|---|---|---|
| **专项威胁类型** | 设备原生五类 `apt` / `vul_0day` / `cybercrime` / `webshell` / `mining`（`tdp_dashboard_status` 威胁简报切面）+ 逐条的 `threat.is_apt` | 报告 3.1 横切索引 |
| **攻击方向** | `direction` / `direction_desc` → Compromised / Lateral Movement / Inbound Attack | 报告 3.2 详情主体，排序即紧迫度 |
| **可信性定性** | 下面 §4.1 的三分法 | 每条发现的属性标注，**不分节** |

再加 **kill chain 阶段**（`threat.phase`，配合 `attack_chain` 的 `phase_counts`）作为位置标注。

**APT / 0-day 命中时必须上浮**到执行摘要和优先队列——这两类天然量少，
留在分类索引里等于没报。

> **不做 ATT&CK 映射。** TDP 3.3.8 接口不返回 tactic / technique 字段，硬映会引入错误归类。
> 客户明确要 ATT&CK 就单独提出来人工做，**skill 不自动生成**。

### 4.1 流量定性三分法（唯一强制人审点）

每个进入研判的事件，结论必须落到四档之一，**不许跳过、不许默认**：

| 定性 | 特征 | 报告里的去处 |
|---|---|---|
| `real_threat` | 命中情报、`is_connected=1`、`result=success`、真实数据外流 | Threat Findings · Confirmed |
| `capability_validation` | **模式 A 专用**：我方模拟攻击/投放样本 | 单独成节，**绝不混进真实发现** |
| `customer_own_behavior` | 客户自有安全工具／运维／员工行为——真实但非攻击 | Items for Confirmation（只有客户能认领） |
| `tdp_artifact` | 统计假象、机制产物 | 附录，说明为何排除 |
| `pending_review` | 证据不足以定论 | Items for Confirmation，列证据 |

### 4.2 失陷判定优先级

1. `threat.is_connected = 1`（C&C 建连成功）—— **最硬信号，优先级高于"攻击成功"**
2. `threat.characters` 含 `is_compromised`
3. `threat.result = 'success'`

失陷主机必查**次生行为**：有没有再对内横移／对外攻击。失陷 + 扩散 = 定级上调。

`result = unknown` **不等于**没成功。旁路检测无法确认结果时，结合目标补丁状态和后续行为判断。

### 4.3 扫描器 vs 真实横移（三条同时成立才下结论，全部用相对量）

1. 单源打击的**目标数量级**远高于全网中位数
2. **威胁种类爆炸**——一台主机涌现大量互不相关的漏洞家族
3. 结果**以失败/未知为主**

**绝不用绝对阈值**（"打了 100 个目标""超过 5000 条"），换个环境立刻失效。

模式 A 下，这类特征极可能就是我方的攻击模拟器——**先和用户核对**再定性。

### 4.4 保命清单（无条件逐条进研判，不参与任何折叠）

`is_connected=1` / `is_compromised` / `result=success` / `is_apt=1` / `severity=4` /
`threat.type` ∈ {trojan, rat, shell, dc, tunneling}。

最后一条最关键：**这类告警天然量少**，纯按告警量排序必然把它们埋进长尾，
而它们恰恰是巡检最该找的东西。

### 4.5 交叉关联（最有价值的产出）

把攻击面层和威胁层 join，每条结论必须带**两维依据**（资产侧 + 威胁侧），只有一维的不进队列：

| 优先级 | 规则 |
|---|---|
| **P0** | 弱口令 `result=success` 且该资产对外暴露 |
| **P0** | `is_compromised` 且该主机自身对外提供服务 |
| **P0** | 资产对外暴露 且 存在 `result=success` 的告警 |
| **P1** | **有告警的 IP 不在资产表里** → 资产台账缺失 + 可能有监控盲区 |
| **P1** | `direction=lateral` 的源主机 且 该主机有对外服务（内部跳板） |
| **P2** | 资产暴露 + 弱口令/脆弱性，但无相关告警（隐患未被利用） |

设备自己的报告不做这个 join，**真正的高危恰恰只在交叉处出现**。

---

### 4.6 IOC 富化配额（硬上限）

- **只对保命清单条目富化**，且**单次巡检最多 20 个 IOC**。超出的按严重度排序取前 20，
  其余标 `not_enriched — quota`，在附录列出待人工。
- **先用设备自带的攻击者 IP 信誉**（incident 二级查询），它能覆盖的就不要再调外部情报接口。
- 只用 `threatbook_io_*`。**禁止** VirusTotal / AbuseIPDB / 任何第三方源。
- 富化失败标 `not_enriched`，**绝不编造来源、链接或结论**。

## 5. 成文

报告骨架、每节写法、措辞原则、术语表见 `references/report-template-en.md`。

要点：

- 正文**英文**，术语对齐 TDP 产品英文 UI，**不自创译法**
- `coverage_gaps` 非空时，**第一页必须有可信度声明**
- 每节数字标注时间语义（"In the last 24 hours" vs "As of \<ts\>"）
- **填平 Security Recommendations**——这是相对设备自带报告的主要增量
- 模式 A 下，capability validation 单独成节
- **长度控制**：正文只逐条展开「保命清单 + 帕累托头部（累计到 80%）」，其余折叠成统计桶
  放附录。**目标：正文发现条目不超过 40 条。** 超了说明降噪没做够，回 Phase 6 重新折叠，
  **不要直接把几百条堆进报告**——没人看的报告等于没写

## 6. 红线（不可协商）

1. **严格只读。** `tdp_policy_settings` 和 `tdp_platform_config` **绝不调用**——
   它们能加黑名单、联动阻断、改告警处置状态、改配置。**巡检工具不改变被巡检对象。**
   即使用户在对话里说"顺手帮我把那个 IP 封了"，也要拒绝并说明这不是巡检的职责。
2. **不落明文口令。** 弱口令接口强制 `is_plaintext = false`；报告只写用户名、
   口令长度与强度特征、命中规则，**绝不写口令内容**。
3. **IOC 富化只用 ThreatBook 情报**（`threatbook_io_*`）。**禁止** VirusTotal / AbuseIPDB /
   任何第三方源参与 IOC 定性——这些工具在环境中可能是启用状态，看到也不要用。
4. **只写实际查到的。** 未富化的标 `not_enriched`，**绝不编造来源、链接或结论**。
   也不要写"公开源查不到"这类未经授权的来源对比。
5. **客户数据不外发。** 内网 IP、主机名、账号、资产拓扑只落本地 Workspace。
6. **不替客户拍板。** 生产环境流量的定性存疑时一律 `pending_review`，列证据交人裁决。
7. **不夸大。** 模式 A 下把我方打的攻击写成"环境中发现的真实威胁"是最严重的失误。
