# 研判规则详解

定性拿不准时读这里。所有判据只用 TDP 原生字段，**不含任何客户特定的数字**。

---

## 1. 失陷判定

**信号强度排序**（从硬到软）

1. `threat.is_connected = 1` —— C&C 建连成功。**最硬**，优先级高于「攻击成功」，
   因为它证明的是通道已建立，不只是某次攻击奏效。
2. `threat.characters` 含 `is_compromised` —— 设备的失陷标记。
3. `threat.result = success` —— 攻击成功，但不必然等于持久化失陷。
4. `threat.is_apt = 1` —— 命中黑客组织归因，定级上调。

**必做两件事**

- **IOC 富化**：把域名 / IP / 哈希交给 ThreatBook 情报接口，确认家族归属、是否在野、信誉。
  云情报不可达时标「未富化·待人工」，**不要用第三方源顶替**。
- **反查次生行为**：这台主机有没有再对内横移／对外攻击。
  失陷 + 已扩散 -> 定级上调，处置窗口收紧。

**同一 IOC 命中多台主机** -> 可能同源批量感染，报告里要关联呈现，不要拆成孤立条目。

**建连未成功不等于主机干净**。典型场景：恶意程序在主机上持续尝试外连，但域名解析被上游拦截。
此时正确表述是「恶意程序已驻留并持续尝试外连，但连接未建立」——
既不能据此说「已发生数据外泄」，更不能因为没建连就判定主机干净。
上游拦截是单点防护，不是修复。

---

## 2. 扫描器 vs 真实横移

**三条同时成立**才能下扫描器的结论，且**全部用相对量**：

| 判据 | 相对基线写法 |
|---|---|
| 目标数量级 | 单源 `distinct(dst)` 显著高于全网中位数（默认 5 倍） |
| 威胁种类爆炸 | 单源 `distinct(threat.name)` 超过阈值（默认 10），且覆盖互不相关的漏洞家族 |
| 结果分布 | `result` 以 `failed` / `unknown` 为主 |

> **绝不写死绝对数字**。「打了 100 个目标」在大网里是常态，在小网里是异常。

**三条齐了之后，还没完**——在纯真实流量模式（模式 B）下，它可能是：

- 客户自己的漏扫 / BAS / 红队工具 -> `customer_own_behavior`
- 客户内网一台被控主机在横扫 -> `real_threat`

**这两种天差地别，只有客户能认领。** 给倾向和依据，标 `pending_review`，交人裁决。

---

## 3. 业务行为识别

**特征**：时间间隔高度规律（变异系数极低）+ `result != success` + 目标是自有资产 + 响应码正常。

规律性是关键信号，但它指向两个相反的方向：

- 业务轮询 / 计划任务 -> `customer_own_behavior` 或误报
- 蠕虫 / 自动化脚本 / 定时暴破 -> `real_threat`

**区分点**：看目标和结果。打自有业务接口且响应正常 -> 业务；打认证接口且大量失败 -> 暴破。

---

## 4. 隧道与远程访问

`threat.type = tunneling` 即使量小也要单独拎出来，**不能因为「只有几条」就折叠掉**。

**为什么危险**（这几条是定性依据，写报告时直接用）：

1. **绕过边界管控** —— 对防火墙表现为普通出站加密流量
2. **加密不可审计** —— 旁路只能看到握手信息，看不到隧道内容
3. **常态化通道** —— 只要进程在跑，外部即可直连内网
4. **责任边界不清** —— 第三方账号泄露等同内网直连权限

**定性**：这通常是**治理问题**不是恶意软件问题。结论应该是「要么正式纳管（登记、限定范围、审计、
定期复核），要么移除」——**「不知道它在那里」不行**。

---

## 5. 入站攻击

- 攻击结果为「未成功」的入站是**正面结论**，要写进报告：边界防护有效。
  只报坏消息的巡检说服力反而弱。
- **警惕高频单源**：持续时间极长的「攻击」往往是业务轮询被规则误命中，不是真攻击。
  查它的目标、响应码、时间规律再下结论。
- 云厂商地址段的一次性探测是互联网背景噪声，不是定向攻击。按背景噪声折叠成统计即可。
- **`result = unknown` 不等于失败**。旁路无法确认结果时，结合目标补丁状态与后续是否出现
  横移／外联综合判断。

---

## 6. 部署位置导致的系统性误判

**最容易整片判错的一类**，而且很隐蔽。

**征兆**：某内网 IP 被记为大量不同 CVE 家族的攻击源，且目标集中在少数几台后端。

**验证**：
- 比对 `net.real_src_ip` 与 `net.src_ip` —— 不一致即证明存在代理链
- 看载荷里的 Host 头是否为公网地址
- 看该 IP 的资产类型是否被识别为反向代理

**结论**：这是**入站攻击**被记成了横移，不是内网横移。要在报告里说明口径修正，
并给调优动作（在代理上为所有 vhost 开启真实源透传 / 把代理登记为资产 / 在 NAT 边界外增加镜像点）。

**验证有效性的正面证据**：当代理正确传递真实源时，设备能还原真实攻击源并完成云资产标签富化——
说明修复方案可行，这本身是很好的调优论据。

---

## 7. 攻击面研判

- **暴露 + 高危端口 + 弱口令** 三者叠加的主机优先级最高，等同准失陷。
- 弱口令看**登录结果**：有成功登录记录 = 已被利用。
- **EOL 组件**是结构性风险：无补丁可打，只能迁移或网络隔离，优先级高于普通漏洞。
- **未识别服务**是盲区不是「无风险」，要逐项确认归属与必要性。
- Banner 暴露版本号等于给扫描器提供选择载荷的依据，属于低成本可修项。
- 违规远控软件按**外联目标域名**精确识别到具体软件名，报告里写软件名而不是笼统的「远控软件」。

---

## 8. 定级自洽性

设备的总体态势等级由可调阈值算出，可能与逐项发现不符。

出现「等级偏低但存在确认失陷／成功的后门通信」时：

- 在报告中**明确指出矛盾**，给出复核阈值的建议
- **不盲从**设备定级，**也不擅自改写**——呈现矛盾，给建议，让客户定

---

## 9. 措辞原则

| 模式 | 我方测试流量 | 客户真实流量 |
|---|---|---|
| A（有模拟攻击） | 「检出能力验证」 | 「实网发现」 |
| B（纯真实监听） | 不存在这一档 | 统一「在客户真实环境中检出」——**这是更强的卖点：真网实测，非摆拍** |

模式 B 下再按根因分：
- 真实威胁 / 失陷 -> 「实网发现，建议处置」
- 客户自有行为 -> 「待客户确认归属，属管理面整改项」

**通用**：不夸大、不替客户对真实环境拍板根因。
